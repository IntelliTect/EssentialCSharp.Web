## Getting Started

For information on setting up your local development environment, please see the [Getting Started Guide](docs/getting-started.md).

### Standalone Aspire development

Only this repository is required. Install the .NET SDK selected by `global.json`, Node.js/npm,
the [Aspire CLI](https://aspire.dev/get-started/install-cli/), and a Docker-compatible container runtime.
Start the container runtime first. The root solution builds the hosting library and AppHost but
does **not** include the Docker-backed Aspire tests.

```powershell
dotnet build EssentialCSharp.Web.slnx
aspire start --apphost dev\EssentialCSharp.Web.AppHost\EssentialCSharp.Web.AppHost.csproj --isolated
aspire wait essentialcsharp-web --apphost dev\EssentialCSharp.Web.AppHost\EssentialCSharp.Web.AppHost.csproj
aspire describe --apphost dev\EssentialCSharp.Web.AppHost\EssentialCSharp.Web.AppHost.csproj
```

Use the allocated Web HTTP endpoint reported by Aspire, not a hard-coded localhost port.
`--isolated` keeps worktree container identities separate. SQL Server, pgvector PostgreSQL,
and optional Ollama use persistent data volumes; restart with the same command to retain data.
The AppHost has its own `UserSecretsId`, separate from ordinary Web application secrets.
SQL Server passwords are generated by Aspire unless an AppHost `Parameters:sqlserver-password`
secret is supplied. Stop only this AppHost using `aspire stop --apphost` with the same project path.

Local AI defaults to Ollama (`qwen2.5-coder:7b`, approximately 5 GB download); local vector search
is not enabled. Disable model downloads before starting when chat is unnecessary:

```powershell
dotnet user-secrets set "Parameters:UseLocalAI" "false" --project dev\EssentialCSharp.Web.AppHost
```

An AppHost `AIOptions:Endpoint` takes precedence over local AI. Configure that endpoint and
optional `AIOptions:ChatDeploymentName`, `AIOptions:VectorGenerationDeploymentName`, and
`AIOptions:SystemPrompt` in the **AppHost** secrets/configuration to forward them to Web.
Cloud authentication remains the existing Web application's responsibility.

Standalone content defaults to the existing placeholders (`/hello-world` is a useful smoke page).
No Tooling, Try.NET, or Host clone is needed. The private content feed requires Azure DevOps
feed authentication and an opt-in AppHost `Parameters:UseNugetContentFeed=true`.
For a cold content-feed build, also restore/build Web with `-p:AccessToNugetFeed=true` before
starting Aspire; changing a runtime environment variable alone does not redo NuGet restore.
Keep the default `false` for public-feed builds.

Run the dedicated development test solution explicitly:

```powershell
dotnet test --solution dev\EssentialCSharp.Web.Aspire.slnx
```

Graph tests do not start containers. The shared `TUnit.Aspire` smoke fixture passes
`--EssentialCSharpWeb:EphemeralDatabases=true` for fresh, session-lifetime databases without data
volumes, disables AI/feed, and checks that migrations finished before Web became healthy, then
`/health`, `/alive`, and placeholder HTML. To run only graph checks, use
`--treenode-filter "/*/*/(AppHostGraphTests|WebHostingExtensionsTests)/*"`.

The AppHost references the Web project so building the AppHost builds Web before the EF migration
resource runs its `--no-build` database update; Web starts only after that update completes successfully.

`EssentialCSharp.Web.Hosting` exposes ordinary Aspire extensions reused by the standalone
AppHost and the aggregate `IntelliTect-dev/EssentialCSharp.Host`:
`AddEssentialCSharpWeb(absoluteWebProjectPath, sqlDatabase, vectorDatabase)` returns Web,
`AddEssentialCSharpContentFeedParameter()` returns the shared parameter handle, and
`web.WithEssentialCSharpLocalAI()` applies the local/cloud policy.
The aggregate Host owns publish infrastructure, content generation, Try.NET, and cross-repo tools.
The application references neither hosting project, and production deployment remains independent.

## Page metadata

The shared layout uses `ViewData["Description"]` for the HTML, Open Graph, and Twitter descriptions; pages without an override use the site-wide fallback. Public page actions set their own descriptions. Chapter pages use `Chapters/sitemap.descriptions.json` when available (generated by ParserCli), or a description based on the chapter heading when the file is absent. Views can also set `ViewData["Description"]` before the layout renders.

The layout renders exactly one canonical link (and a matching `og:url`) for every successful, non-Identity page. Its origin always comes from `SiteSettings:BaseUrl`, so each deployment must set it to its own origin (for example `SiteSettings__BaseUrl=https://dev.essentialcsharp.com` for the dev environment). The request `Host` header is deliberately not used, to avoid host-header poisoning. For chapter pages, the path from the parser-generated canonical is kept (so alias routes such as `/hello-world` point to the primary page) and re-based onto the configured origin; the parser's own `<link rel="canonical">` is removed from the injected head. Other pages use the request path. Query strings are excluded.
