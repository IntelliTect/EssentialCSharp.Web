## Getting Started

For information on setting up your local development environment, please see the [Getting Started Guide](docs/getting-started.md).

### Standalone Aspire development

Only this repository is required. Install the .NET SDK selected by `global.json`, Node.js/npm,
the [Aspire CLI](https://aspire.dev/get-started/install-cli/) version pinned by `sdk.version` in
`aspire.config.json` (`aspire update --self` upgrades an existing install), and a Docker-compatible container runtime.
Start the container runtime first. The single root solution includes the application, hosting
library, AppHost, and all tests. The production Dockerfile restores, builds, and publishes only
the Web project and its dependencies, without loading the Aspire projects.

```powershell
dotnet build EssentialCSharp.Web.slnx
aspire start --apphost dev\EssentialCSharp.Web.AppHost\EssentialCSharp.Web.AppHost.csproj --isolated
aspire wait essentialcsharp-web --apphost dev\EssentialCSharp.Web.AppHost\EssentialCSharp.Web.AppHost.csproj
aspire describe --apphost dev\EssentialCSharp.Web.AppHost\EssentialCSharp.Web.AppHost.csproj
```

Use the allocated Web HTTP endpoint reported by Aspire, not a hard-coded localhost port.
`--isolated` keeps worktree container identities separate. SQL Server, pgvector PostgreSQL,
and optional Ollama use persistent data volumes; restart with the same command to retain data.
The AppHost has its own `UserSecretsId`, separate from ordinary Web application secrets.
SQL Server passwords are generated by Aspire unless an AppHost `Parameters:sqlserver-password`
secret is supplied. Stop only this AppHost using `aspire stop --apphost` with the same project path.
Add `--format mermaid` to `aspire describe` to print the resource dependency graph as a Mermaid diagram.

The Web resource uses Aspire's Project v2 model (`AddDotnetProject`), which the AppHost builds
before launch. Aspire watch [is not yet implemented for Project v2 resources](https://aspire.dev/integrations/dotnet/migrate-dotnet-project-resource/#check-workflows-before-migrating);
after changing Web code, rebuild just that resource with `aspire resource essentialcsharp-web rebuild --apphost <path>`.

Local AI defaults to Ollama (`qwen2.5-coder:7b`, approximately 5 GB download); local vector search
is not enabled. Disable model downloads before starting when chat is unnecessary:

```powershell
dotnet user-secrets set "AIOptions:UseLocalAI" "false" --project dev\EssentialCSharp.Web.AppHost
```

This is startup configuration: restart the AppHost after changing it. It is not a dashboard
toggle. Existing `Parameters:UseLocalAI` secrets remain a fallback, but `AIOptions:UseLocalAI`
takes precedence. Invalid Boolean values fail startup instead of enabling a model download.

An AppHost `AIOptions:Endpoint` takes precedence over local AI. The **AppHost** forwards that
endpoint and optional `AIOptions:ChatDeploymentName`, `AIOptions:VectorGenerationDeploymentName`,
and `AIOptions:SystemPrompt` to Web, with local AI forced off. Other application options,
including MCP tool permissions, remain Web-owned; configure them directly in Web.
Cloud authentication remains the existing Web application's responsibility.

Standalone content defaults to the existing placeholders (`/hello-world` is a useful smoke page).
No Tooling, Try.NET, or Host clone is needed. The private content feed requires Azure DevOps
feed authentication. Content selection is an MSBuild setting, not a dashboard parameter:
set the environment variable **before** Aspire restores/builds the AppHost and its Web project reference.

```powershell
$env:AccessToNugetFeed = "true"
aspire start --apphost dev\EssentialCSharp.Web.AppHost\EssentialCSharp.Web.AppHost.csproj --isolated
```

Keep it unset or `false` for public-feed builds. To switch sources, stop Aspire, change the
environment variable, then start again with a rebuild; do not use `--no-build` or conflicting
`-p:AccessToNugetFeed` overrides. The old `Parameters:UseNugetContentFeed` dashboard setting
cannot control MSBuild and has been removed. If previously enabled, remove it from AppHost
secrets/configuration before starting:

```powershell
dotnet user-secrets remove "Parameters:UseNugetContentFeed" --project dev\EssentialCSharp.Web.AppHost
```

Run all tests, including the Docker-backed Aspire smoke tests, from the root solution:

```powershell
dotnet test --solution EssentialCSharp.Web.slnx
```

Graph tests do not start containers. The shared `TUnit.Aspire` smoke fixture passes
`--EssentialCSharpWeb:EphemeralDatabases=true` for fresh, session-lifetime databases without data
volumes, disables AI/feed, and checks that migrations finished before Web became healthy, then
`/health`, `/alive`, and placeholder HTML. It also starts a second AppHost and verifies both Web
instances remain healthy on distinct URLs. Smoke tests are skipped when no Linux container engine is
reachable (for example hosted macOS runners or Windows runners with only Windows containers), except
in Linux CI where they always run. Graph tests also generate a local manifest to verify that publish
mode contains no migration tools, browser helpers, local AI, or Development environment override.
To run only graph checks, use
`dotnet test --project dev\EssentialCSharp.Web.AppHost.Tests --treenode-filter "/*/*/(AppHostGraphTests|WebHostingExtensionsTests)/*"`.

Browser journeys share the fresh-database fixture. The reading journey opens and filters the TOC,
selects a chapter, follows next/previous links, and verifies a rendered section heading both from
its TOC link and a fresh anchored URL load. It uses the repository's `introducing-c` / `hello-world`
placeholder mappings locally; the deployed version discovers links from the real TOC, without
production-only chapter keys or login credentials. Generated aliases can serve the same document:
TOC links retain anchors, while arrow buttons deliberately omit them. The shared journey makes
five content requests (plus two home loads), keeping a deployed suite run below the anonymous
10/minute and 20/hour content limits when run once. Concurrent or repeated runs share the IP budget.

Run only the local reading journey after installing Playwright Chromium:

```powershell
dotnet test --project dev\EssentialCSharp.Web.AppHost.Tests --treenode-filter "/*/*/ReadingJourneyTests/*"
```

`DeployedReadingJourneyTests` runs with the existing `Category=Deployed` promotion gate and
six-hour scheduled checks when `E2E_BASE_URL` is set. No extra workflow or secrets are required.

The AppHost references the Web project so building the AppHost builds Web before the EF migration
resource runs its `--no-build` database update; Web starts only after that update completes successfully.

`EssentialCSharp.Web.Hosting` exposes ordinary Aspire extensions reused by the standalone
AppHost and the aggregate `IntelliTect-dev/EssentialCSharp.Host`:
`AddEssentialCSharpWeb(absoluteWebProjectPath, sqlDatabase, vectorDatabase)` returns Web with
Aspire-allocated ports and named database references, and
`web.WithEssentialCSharpLocalAI()` applies the local/cloud policy.
Migrations and browser helpers are registered only in run mode. The aggregate Host owns
full-stack infrastructure, content generation, Try.NET, and cross-repo tools.
The application references neither hosting project, and production deployment remains independent.

## Page metadata

The shared layout uses `ViewData["Description"]` for the HTML, Open Graph, and Twitter descriptions; pages without an override use the site-wide fallback. Public page actions set their own descriptions. Chapter pages use `Chapters/sitemap.descriptions.json` when available (generated by ParserCli), or a description based on the chapter heading when the file is absent. Views can also set `ViewData["Description"]` before the layout renders.

The layout renders exactly one canonical link (and a matching `og:url`) for every successful, non-Identity page. Its origin always comes from `SiteSettings:BaseUrl`, so each deployment must set it to its own origin (for example `SiteSettings__BaseUrl=https://dev.essentialcsharp.com` for the dev environment). The request `Host` header is deliberately not used, to avoid host-header poisoning. For chapter pages, the path from the parser-generated canonical is kept (so alias routes such as `/hello-world` point to the primary page) and re-based onto the configured origin; the parser's own `<link rel="canonical">` is removed from the injected head. Other pages use the request path. Query strings are excluded.

Please use issues or discussions to report issues found.

## IndexNow Setup (Production Deployment)

The deployment workflow notifies search engines (Bing, Yandex, Naver) of content updates via the [IndexNow protocol](https://www.indexnow.org/). After each successful production deploy it submits only the URLs that were added, updated, or removed in that deploy.

### How It Works

1. Before deploying, the workflow snapshots the live `https://essentialcsharp.com/sitemap.xml`.
2. After the smoke test confirms the new version is live, it fetches the sitemap again.
3. It diffs the two: URLs that were added, removed, or whose `<lastmod>` changed are POSTed to `https://api.indexnow.org/indexnow`. If nothing changed, nothing is submitted.
4. IndexNow distributes those URLs to all participating search engines (Bing, Yandex, Naver, etc.).

Book pages get their `<lastmod>` from `sitemap.json` in the content NuGet package. Static app pages (`/about`, `/guidelines`, etc.) have no `<lastmod>`, so they are only submitted when added or removed.

### Setup Requirements

#### 1. GitHub Secret
Generate a random hex key and store it in GitHub repository secrets as `INDEXNOW_API_KEY`. The workflow uses this value both to write the key verification file into the Docker image at build time and to authenticate IndexNow submissions.

Go to: **GitHub repo → Settings → Secrets and variables → Actions → New repository secret**
- Name: `INDEXNOW_API_KEY`
- Value: a random hex string (e.g. generate with `openssl rand -hex 16`)

#### 2. Key Verification File (auto-generated at build time)
IndexNow requires domain ownership proof via a publicly accessible `.txt` file:
- The workflow writes `wwwroot/{key}.txt` (containing the key value) before building the Docker image
- The file is NOT committed to git — it is generated fresh on every CI run from the GitHub Secret
- ASP.NET Core's static file middleware serves it at `https://essentialcsharp.com/{key}.txt`
- IndexNow crawls that URL to verify domain ownership before accepting submissions
- Without this file, all submissions return HTTP 403

The key file is intentionally public — that is by design. The "security" is that only the domain owner can host a file at that path.

### Important Notes
- The IndexNow step uses `continue-on-error: true` — a submission failure will never block a deployment
- Only changed URLs are submitted, per the IndexNow guidance; resubmitting unchanged URLs on every deploy risks submissions being deprioritized
- To rotate the key: generate a new hex string and update the GitHub Secret — the old key file disappears automatically on the next deploy
